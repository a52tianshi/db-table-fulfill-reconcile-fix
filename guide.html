一眼看懂整轮流程

老表扫描 → 缓存一批 → 完整查询新表 → 比较并筛出候选 → 业务事务复核 → 清空缓存继续
老表扫描完成 → 反向扫描新表 → 按批查询老表 → 复核额外记录 → 只报警，不删除

第一遍：从老表找缺失和差异

1逐条扫描老表

Old.Scan 同步产出记录，Records.Key 提取稳定唯一的 identifier。写入注入的 Cache。

尚未满批时继续扫描；缓存不会累计整张表。

2批满后暂停读取

达到 BatchSize 就同步处理整批。查询和复核返回以前，不再读取下一批，这就是背压。

只有 Scan 成功结束，才处理剩余尾批；扫描报错则停止。

3完整查询新表

New.Lookup(keys) 必须完整解析这一批 key。成功结果中缺少 key，才形成“疑似缺失”。

分页不完整、超时或部分失败必须报错，不能把它们当作查无记录。

4缓存比较只筛候选

新表存在且 Records.Equal 相等：跳过。缺失或内容不同：交给 Reviewer.Review。

候选只是线索，不是写入指令；此处没有数据库写操作。

关键区别：不是“一边扫新表，一边把没遇到的 key 当缺失”。每批都通过完整批量查询配对，避免把“尚未扫到”误判为“不存在”。

↓

业务事务边界：重新读取，重新分类

调用方的 Reviewer 开启事务 → 重读老表和新表 → 按新状态再次比较 → 报警或修复 → 提交。框架不替业务控制事务，也不绑定 SQL。

老有 / 新无

只报警模式：报警。
修复模式：从老表插入新表。

两边存在但不同

只报警模式：报警。
修复模式：用老表覆盖新表。

仅新表存在

两种模式都保留并报警，绝不删除。

两端已相等，或者两端都已不存在：跳过。即使候选原先显示“缺失”，也必须以事务内新状态为准。内存示例用同一把锁模拟这个边界。

↓

清空当前批缓存，继续下一批

每批最多缓存 BatchSize 条。当前批处理完成才清空并继续；没有后台候选队列。老表完整扫描并处理尾批以后，才能进入第二遍。

第二遍：找仅新表存在的记录

New.Scan → 缓存一批新表记录 → Old.Lookup(keys) 完整查询 → 老表查无记录 → Extra 候选 → Reviewer 重读两端并重新分类

这次扫描专门发现额外记录。复核后若依然只有新表存在，保留并报警；若并发变化让它变成其他情况，则按最新状态处理。核心没有删除接口。

接口分别负责什么

  • Source：流式扫描和完整批量查询；负责底层查询、分页、扫描快照和 context 传播。
  • Records：提取唯一键，定义业务内容相等；忽略哪些字段由调用方决定。
  • Cache：保存当前批次；不可静默淘汰。默认 MemoryCache 有条数限制。
  • Reviewer：事务重读、最终比较、告警与可选修复；不得直接信任候选快照。
  • Engine：串行编排两个方向的分批配对、候选分发、清理与失败返回。

运行、失败与一致性

如何运行示例

在仓库根目录执行 go run ./cmd/demo。先运行 AlertOnly，再运行 Repair；示例最终保留额外记录，补齐缺失记录，覆盖不同内容。

验证命令：go test -race ./... 和 go vet ./...。需要 Go 1.22+，无第三方依赖。

有界内存和取消

引擎缓存、key 和查询结果均为 O(BatchSize)，按条数而非字节计算。驱动与扫描器也需限制缓冲。内存示例复制全量 key，仅用于演示；生产应实现 keyset 分页并定义快照边界。

取消通过 context 传播，不能强制终止不响应取消的业务回调。Engine 和缓存不能在多轮并发运行间共享使用。

错误如何处理

扫描、查询、缓存或复核任一失败，立即停止并返回部分统计，错误支持 errors.Is。已经提交的批次不回滚，业务处理须支持幂等重跑。Candidates 表示复核调用次数，不表示已确认修复数量。

“在线使用”不等于完整不停机迁移保证

事务复核只保护已发现的候选。并发修改仍可能造成扫描遗漏、重复候选或相等记录随后变化，不能保证单轮全局收敛。生产需结合一致性快照、高水位、版本校验、CDC 或定期重跑。

同 MySQL 实例可让业务复核共享事务；锁、唯一约束、缺失行的并发插入竞争及重试由适配器处理。跨实例需要独立的一致性方案。

当前 MVP 不含全量复制、增量同步、切流、持久化进度或真实 MySQL 适配器。
