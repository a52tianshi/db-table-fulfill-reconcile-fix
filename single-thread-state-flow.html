把三种状态分别看清

每张物理表

未开始 → 扫描中 ↔ 缓存满暂停 → 扫描结束；查询失败是失败，不是 EOF。游标只被对应扫描推进。

每个批次

扫描页入内存 → 分 shard 配对 → 初比 → 复核批攒批 / 就绪 → 事务重读 / 分类 → 分操作写入 → 提交确认 → 排空。

每条 key

等待配对 → 等待初比 → 相等完成 / 候选待复核 → 事务复核中 → 待插入 / 待更新 / 待报警 / 跳过 → 等待提交 → 确认完成。

单线程调度的具体判断

  1. 是否已有需要收尾的事务？有：继续读、分类、写入、提交或回滚；不去扫描下一页，不开启第二个事务。
  2. 当前页是否仍有未完成 shard / 复核批？有：处理下一个复核批或分片，先排空当前页。
  3. 当前页是否全部完成？是：回收内存，推进该页安全游标，再取下一页。
  4. 老表是否真正 EOF？成功读取空页后才进入反向扫描；失败、取消不等于 EOF。
  5. 反向扫描是否还有页 / shard？有：取一页新表数据，复用批量查询、比较与事务复核逻辑。
  6. 所有扫描与批次结束且无未决结果？是：本轮完成；否则不能只因两边“扫描读完”就结束。

设计采用主动排空当前页的单线程调度，没有多个 worker，没有“扫描线程 + 写线程”同时跑。多个记录可以同时处于等待状态，但实际执行一次只推进一个批次动作。事务内的待插入 / 待更新是短暂分类，不是解锁后排长队。

错误与安全游标

  • 完整查询失败：不产生缺失结论；停止或显式重试完整查询。
  • 事务内失败：先回滚再返回失败；当前批暂存数据不算修复成功。
  • 提交结果未知：不能假定回滚，也不能假定成功；冻结相关进度，按业务协议重读并幂等确认。
  • 取消发生在活动事务内：必须先处理事务的提交/回滚/未知结果；本演示的取消场景发生在 BEGIN 前。
  • 老表已读到 50，但某片仍有候选：安全游标仍不推进到 50。进程重启后的检查点持久化由后续实现负责。

    有界与背压

    默认先扫描 50 条，Memory 上限也是 50；每页排空后才继续读。每 shard 的复核批最多 8 条、每条 INSERT 最多 4 条，UPDATE 每次 1 条。页尾不足阈值立即发批。

    同一事务重读并写入

    复核攒批在事务外。开启事务后按顺序重读老表、新分片，重新分类，批量插入与逐条更新，再提交。事务内不等下一扫描页来凑批。

    单线程 ≠ 数据库没有并发写

    框架单线程一次执行一个动作；业务仍可并发修改。真实适配器负责锁、隔离级别、唯一约束、版本校验及提交结果不确定时的恢复。

    这是设计模拟，不调用数据库。Go 库（reconcile + mysqltable）已实现分片路由、分页扫描、按分片的批量复核与插入事务、逐步重试和进度回调；本页的逐 key 状态计数、检查点等仍是设计，尚未实现。页尾背压时必须立即处理已有尾批，不能只等计时器或未来页面来凑满。线上还需字节/参数预算、最大等待时间、检查点持久化及明确扫描边界。
