# 离线设计演示的维护

仓库根目录的两个 HTML 均自包含，无外部资源依赖，可以直接离线打开：

- `batch-scan-demo.html`：默认 50 条分布 5 个 shard，13 种场景。
- `single-thread-state-flow.html`：单线程整体状态流转图，复用同一模型；节点可定位实际步骤。

它们仅演示下一版设计，不连接数据库，不修改 Go 核心。原 `guide.html` 保留简短 16 步说明，新页面提供更细的展开。

## 修改和重新生成

编辑本目录 `simulation.js`（确定性模型）、`view.js`（交互）、`style.css`（样式）或 `build.py`（页面/流程图），然后在仓库根目录运行：

```sh
python3 docs/visuals/build.py
node docs/visuals/check.cjs
```

生成器把模型、交互、样式嵌入两个独立 HTML，不需要 HTTP 服务、npm 安装或网络连接。

## 模型约定

- 默认扫描一页 50 条；缓存最多 50 条，当前页排空后才读取下一页。尾页场景为 17+17+16。
- 按配置路由归组，默认取 `(id-1)%5+1` 只是演示路由，不代表真实业务按 identifier 分片。
- 复核批最多 8 条；单次插入子批最多 4 条；更新每次只处理 1 条；一个事务只处理一个目标 shard。
- 不支持批量更新。每条 UPDATE 只处理一个 key；共享一个事务不等于批量更新 SQL。
- BEGIN → 重读老表 → 重读新分片 → 重新分类 → 按操作分批写入 → COMMIT，顺序执行。未确认提交的写入不计成功。
- 无动态 writer，只有“候选过期”场景显式模拟一次事务前外部变化。事务、锁及故障是逻辑模型，不是真实 DB 实现。
- DB 动作计数为模型动作数；不等于生产 SQL/网络包数或性能测量。
- 内存计数是驻留量，累计结果包含反向扫描重复处理次数。完成后额外记录保留。
- 提交响应丢失场景设定服务端确实提交，随后重读确认。真实系统的未知提交恢复、幂等告警、锁/缺失行竞争和检查点持久化仍需业务实现。

## 验证覆盖

`check.cjs` 检查 13 场景：最终数据、额外记录保留、查询失败不判缺失、回滚不提交、只报警零写入、Memory 上限与 key 唯一、复核批上限、游标、100 空/非空分片和尾页。

页面另经真实无头浏览器验证：首批 50 条、分片筛选、各场景结局、流程节点定位和窄屏无页面级横向溢出。验证无需操作或运行仓库中的 MySQL e2e。
